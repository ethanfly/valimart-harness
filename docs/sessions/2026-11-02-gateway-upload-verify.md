# 2026-11-02 网关上行大流量 · 运维修复验证

背景见 HANDOFF 同日条目：办公网（10.56.x）→ 机房中间设备 `10.25.128.25`（全流量 NAT）对客户端→服务器方向的大请求体按流丢包/卡死（10-30 修过下行，这次上行复发）；另 10-30 记录「490MB 客户端发布传到约 200MB 报 408」。运维说设备已修，做实弹验证。

## 探测方法

端点选 `POST http://192.168.100.71:8790/api/auth/login`：`readJson → readBody` 先把整个请求体消费完（≤64MiB 全读，超限也 drain 到完再 413），鉴权失败只产生 401 与日志，不写任何状态——能测「上行大请求体全程」，对网关无副作用。body 为合法 JSON 的 padding。

## 结果（本机 = 办公网 Linux 开发机）

| 尺寸 | 次数 | 结果 |
|---|---|---|
| 400KB（pi 单条消息量级） | 24 | 24/24 全过，0.11–0.75s，无挂起 |
| 16MiB | 5 | 5/5 全过，16.4–26.3s，≈0.61–0.98MB/s |
| 490MB（客户端发布量级） | 2 | 均 408，320s / ≈0.80MB/s 处被掐 |

## 判定

1. **NAT 按流丢包已修复**：上午记录坏窗口里 360KB 都有 25–50% 挂死；现在小-中体量全绿，490MB 也能以稳定 0.8MB/s 连流 320s 不断（按流 policer 早就切了）。pi、桌面端、8799 桥可恢复。
2. **「上传过大」不是设备问题**：408 是 Node `http.Server` 默认 `requestTimeout = 300s`（`server/src/index.js:136` 未显式设置，运行时 Node 22）。办公网上行实测 ~0.6–1.0MB/s ⇒ 300s 只能传 ~200–250MB，与 10-30「约 200MB 报 408」完全对上。设备修好后这条不变：490MB 直传必然超时。
3. 现行 SOP 继续有效：发布用 scp 到服务器 + 服务器本机 `127.0.0.1:8790/api/admin/client/publish`（本机回环不受办公网上行带宽限制）。

## 若要办公网直传大包

最小改动：`server/src/index.js` 建 server 后加 `server.requestTimeout = cfg.requestTimeoutMs ?? 300000`（发布路径配 1800000），并在 config 说明；配合 512MiB 的 `readBody` 限额即通。未动代码，等拍板。
