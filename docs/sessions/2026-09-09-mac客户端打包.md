# macOS Intel 客户端打包（Windows 构建机直出 zip）

日期：2026-09-09
作者：ethan（管理员，技术部）
需求：用户「帮我打包一个 mac 端的客户端，cpu 是 intel 的」。
产物：`dist/valimart-harness-0.1.0-20260909.0203-mac-x64.zip`（208.9 MB，内含 `valimart harness.app`）。
命令：`npm run dist:client:mac`（= `node scripts/build-mac-client.mjs`）。

## 1. 为什么不能用 electron-builder

- `app-builder-lib/out/packager.js:368` 在 Windows 上直接抛
  `Build for macOS is supported only on macOS`——`--mac` 这条路是封死的，不是配置问题。
- 即使绕过，Windows 侧的 7z 会毁掉 `.app`：
  - `Electron Framework.framework` 等有 **14 个符号链接**（`Versions/Current → A` 等），
    Windows 解压/再压缩会把它们展开成普通文件；
  - Windows 写的 zip 没有 unix 权限位，macOS 解压后主可执行没有 +x，双击直接打不开。
- 结论：**自己读官方 zip、自己写 zip**。新增 `scripts/lib/zip.mjs`（中央目录读 mode/symlink，
  写出时原样还原 + 支持 0755 与 symlink 条目），零依赖。

## 2. 内核（kernel.tar）的跨平台改造

内核 JS 与平台无关，但 npm 在 Windows 上只装了 win32-x64 的 optional 平台包。打 mac 包时必须：

| 动作 | 包 |
| --- | --- |
| 注入 darwin-x64 | `@img/sharp-darwin-x64` + `@img/sharp-libvips-darwin-x64`、`@koromix/koffi-darwin-x64`、`@vscode/ripgrep-darwin-x64`、`node-addon-require-builtin-darwin-x64` |
| 删除 win32-x64 | 上面对应的 4 个 win32 包（含 sharp 的 libvips DLL，省 30+ MB） |
| 保留 | `node-pty/prebuilds/darwin-x64/{pty.node,spawn-helper}`（tarball 自带，`shouldPrune` 按目标平台留） |

`scripts/lib/mac-kernel.mjs` 用「找 win32 对应包所在目录 → 把 darwin 包解到同一个 node_modules」
的方式定位目标目录，不写死路径，内核目录结构变了也能跟上。

### 可执行位

Windows bsdtar 打的 kernel.tar 里所有文件都是 0644，但两个文件必须可执行：

- `node-pty/prebuilds/darwin-x64/spawn-helper`（`unixTerminal.js:31` 直接 exec 它）
- `@vscode/ripgrep-darwin-x64/bin/rg`

修在**运行时**：`scripts/lib/bootstrap.mjs` 解压内核后调 `chmodKernelExecutables()`，
路径判定见 `shouldExecKernelFile()`。这样网关以后下发的 Windows 打的 kernel.tar 也一样能修。

## 3. Node 版本：为什么不用 26

| 版本 | Mach-O `LC_BUILD_VERSION` minos | 结论 |
| --- | --- | --- |
| Node 26.7.0 darwin-x64 | **13.5** | macOS 13.0~13.4 起不来 |
| Node 24.20.0 darwin-x64 | 13.5 | 同上 |
| Node 22.23.2 darwin-x64 | **11.0** | 采用 |

Electron 44.1.1 的 `LSMinimumSystemVersion` 是 13.0，所以整包门槛 = **macOS 13.0**。
Node 22 兼容性验证：用 Windows 版 node 22.23.2 跑内核 `--dump-default-config` 通过、
真启动到 HTTP 401（正常，需令牌）、`node:sqlite` 免 flag 可用（内核 `dsh-session-query-sqlite` 依赖它）。

## 4. 组装 .app（`scripts/lib/mac-app.mjs`）

1. 读 Electron 官方 zip 的条目，按 unix mode / symlink 搬进目标 zip；
2. 改名：`Electron.app → valimart harness.app`、`Contents/MacOS/Electron → Contents/MacOS/valimart harness`、
   四个 `Electron Helper(…).app` → `valimart harness Helper(…).app`（目录、可执行、Info.plist 一起改，
   否则 Electron 按「主 bundle 名 + " Helper"」找 GPU/Renderer 子进程会失败）；
3. 改 `Info.plist`（`CFBundleExecutable/Identifier/Name/IconFile/Version`）与 Helper plist（bundle id / 名称）；
4. 写 `Contents/Resources/{app,payload,icon.icns}`；图标用内核里的 sharp 缩 32/64/128/256/512/1024 生成 icns；
5. 保留 `LICENSE` / `LICENSES.chromium.html` 到 `Contents/Resources/`。

## 5. 验证（构建机上能做到什么程度）

`node scripts/build-mac-client.mjs --verify-only <zip>` 自动检查：

- 639 个条目全部有 unix 权限位；主可执行与 4 个 Helper 可执行 = 0755；
- 14 个符号链接存在且指向正确；
- `Info.plist` 关键键正确、Helper 改名正确；
- `kernel.tar` 里 7 个关键原生件都是 Mach-O **x86_64**，且没有 `.dll`/`.exe`/win32 包残留；
- 随包 `runtime/node` 是 Mach-O x86_64。

另做了一次「假首次启动」：把 payload 用 Windows node 跑 `bootstrap.mjs --packaged`，
解压内核 → 打补丁 → 装 `desk-app` profile（3 个公司插件 + 3 个 profile 插件全部 link）→ 返回 `ready`。
原生模块在 Windows 上加载失败被 `ensureProfile` 的 try/catch 吞掉，不影响这条编排链路的验证。

**未做**：真 Mac 实机启动（没有机器）。交付时已明确告知，并给了排障路径（启动页 + `~/.company-desk/logs/desktop.log`）。

## 7. 真机回归第一轮：fs-ext 缺件（已修）

第一版在 Mac 上启动报「内核进程意外退出（1）」，日志（`~/.company-desk/logs/desktop.log`）：

```
Cannot find module './build/Release/fs_ext.node'
  ← kernel/.../node_modules/fs-ext/fs-ext.js
  ← @deepseek-ai/dsh-session-persistence-jsonl   （POSIX 会话写锁）
```

`fs-ext` 是**安装时 node-gyp 现场编译**的 NAN 原生模块（不是带 prebuilds 的平台包），
Windows 构建机上只会编出 win32 版，而且公司补丁 `company-session-posix-flock-v1`
让 Windows 干脆不编译它（Windows 走 koffi 命名信号量）。darwin 版既编不出来，也找不到
可用的预编译（NAN 与 Node ABI 绑定）。

修法（`scripts/lib/kernel-native.mjs` 的 `company-session-lock-v2`）：内核里那行改成
**POSIX 优先用编译好的 `fs-ext`，没有就用 koffi 直接绑 `flock(2)`**：

- koffi 是 NAPI，darwin-x64 本来就在包里（Windows 锁也用它），零新增依赖；
- 语义与上游对齐：非阻塞 `LOCK_EX|LOCK_NB`，竞争时回调 `error.code = EAGAIN/EWOULDBLOCK`
  （上游据此抛 `SessionAlreadyOwnedError`），释放靠关闭 fd；
- `koffi.load(null)` 从当前进程取 `flock`，失败再退 `/usr/lib/libSystem.B.dylib`；
- 补丁在 `prepareDarwinKernelStage` 里对内核 stage 应用，v1 → v2 幂等升级；
- 打包验证会解出该文件、检查 `company-session-lock-v2` / `companyPosixFlock` / `koffi.load` 并跑 `node --check`；
- 单元测试用假 koffi 验证真的以 `(fd, 6)` 调 `flock`、errno=35 映射成 `EAGAIN`。

顺带确认：内核里只有 4 个 `binding.gyp`（sharp 源码、fs-ext、2 份 node-pty），
sharp 走预编译平台包、node-pty 有 prebuilds，所以 fs-ext 是唯一的「现场编译」漏网之鱼。

## 8. 另外两处 mac 专属处理

- **启动失败可诊断**：`desktop/main.js` 记住内核最后 12 行输出，写进错误弹框（Windows 也受益）。
- **mac 关闭自更新**：网关 `/api/client/download` 下发的是 Windows NSIS 安装器，内核 tar 也是网关
  构建机平台的产物——在 macOS 上套用会搞坏客户端。`desk-host` 的 `scheduleClientUpdate` /
  `scheduleKernelUpdate` 与 `desktop/main.js` 的 `preOpenUpdateCheck` / `maybeApplyPendingClient`
  都加了 `process.platform === 'win32'` 门。mac 客户端用整包替换升级。
- **App Translocation**：日志里 payload 路径是 `/private/var/folders/.../AppTranslocation/...`，
  说明用户是直接在下载目录里启动的。能跑（状态都在 `~/.company-desk`），但安装说明里要求拖进 `/Applications`。
