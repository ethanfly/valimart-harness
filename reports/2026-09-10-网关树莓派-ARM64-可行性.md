# 公司网关（服务端）在树莓派 ARM64 上的可行性评估

- 评估对象：`company-harness` 仓库里的公司网关 `server/`（README 称 "valimart harness Gateway"），即默认 `http://<服务器>:8790` 那个 Node 服务端
- 目标环境：树莓派 + 飞牛 OS ARM 版（Debian 系）+ Docker
- 结论一句话：**服务端代码本身 100% 能跑在 ARM64（纯 JS、零第三方依赖），不需要模拟器；唯一障碍是官方发行包自带的 Node 运行时是 `linux-x64` 的，在树莓派上跑不起来。用 Docker 换一个 arm64 的 Node 运行时即可，或者给官方 Linux 包换掉 `runtime/bin/node`。**
- 结论性质：代码与构建脚本层面已核到证据（下文均有文件行号）；**没有真机验证过（本机无树莓派）**，首次上机请按 §5 验收。

---

## 1. 判定：能跑，缺的只是「运行时架构」

| 检查项 | 结果 | 证据 |
| --- | --- | --- |
| 有没有第三方 npm 依赖 | **没有**，`server/` 无 `package.json`，全仓仅 `devDependencies` | `package.json`（只有 esbuild / playwright / mdast）；`server/` 目录下只有 `src/  skills/  config.json` |
| 源码里的 import | 只有 `node:*` 内置模块 + 仓内相对路径 | 对 `server/src/**` 全量扫 import，非 `node:` 非相对路径的结果为 **0 条** |
| 原生扩展（.node / 预编译二进制） | **没有** | 同上；SQLite 用 Node 22+ 自带的 `node:sqlite`，不是 `better-sqlite3` | 
| 数据库 | `node:sqlite` 的 `DatabaseSync`，纯内置 | `server/src/store.js:2,8,160` |
| Windows 专有代码 | **没有** | 全量扫 `win32 / platform === 'win' / icacls / powershell`，命中的全是正则 `exec(` 和 `.exe` 字样 |
| 路径处理 | 统一 `node:path`，Linux 安装脚本本来就有 | `installer/gateway/install.sh`、`installer/gateway/init-linux.mjs` |
| **官方 Linux 发行包架构** | **`linux-x64`，树莓派跑不了** ← 唯一的坎 | `installer/pins.json` → `nodeLinuxX64` = `node-v25.2.1-linux-x64.tar.gz`；`scripts/lib/gateway-linux.mjs:14-51,112` 硬编码 x64 |
| 官方 ARM64 运行时是否存在 | **存在**，版本对得上 | 本机实拉 `https://nodejs.org/dist/v25.2.1/SHASUMS256.txt`，有 `node-v25.2.1-linux-arm64.tar.gz`，sha256 `b9f6a97e…`（未在本机下载校验） |

也就是说：**服务端对 CPU 架构没有原生依赖，是「解释执行 + 内置模块」的服务**，换运行时即换架构。这和客户端（Electron + node-pty / sharp / ripgrep 一堆平台原生包）完全是两回事——**只有服务端能这么轻松上 ARM64，客户端不能。**

## 2. 树莓派上能跑成什么样（架构层）

- 网关职责：公司账号登录 / 按人签发可吊销令牌 / `/v1` 模型代理（chat + 生图，密钥不出服务端）/ 按人记账限额 / 任务卡四格验收 / 公司盘（`drive/` 目录 + sqlite）/ 管理页 `/admin`。
- 这些都是 HTTP + 文件 IO + SQLite，**没有转码、没有重计算**。模型推理在上游厂商，网关只做转发和记账。
- 所以 Pi 5（4GB/8GB）跑一个几十人规模的网关是**绰绰有余**的；瓶颈不会在 CPU，而在：
  1. **存储**：公司盘镜像 + sqlite + 会话产物，建议数据目录放 SSD/NVMe，不要放 SD 卡（频繁小写伤卡）；
  2. **内存**：进程常驻约百 MB 量级（Node 基线 + sqlite 页缓存），8GB 机器随便跑，4GB 也够；
  3. **上行带宽**：如果员工都走代理，网关是本地到上游的公网出口，这条线才是真实瓶颈。

## 3. 方案 A（推荐）：Docker 跑源码，用官方 arm64 Node 镜像

优点：不改代码、不重新打包、不依赖官方 x64 发行包；升级 = `git pull` + 重启容器。

```bash
# 1) 代码（飞牛上任意目录，例如 /vol1/docker/valimart-gateway/app）
git clone <本仓库> valimart-gateway
cd valimart-gateway
#    只需要这些：server/  scripts/  plugins/desk-ui/src/client/assets/  package.json

# 2) 配置：网关优先读 server/config.local.json（不入库、升级不覆盖）
mkdir -p /vol1/docker/valimart-gateway/data        # 数据目录（建议放 SSD 卷）
cat > server/config.local.json <<'JSON'
{
  "host": "0.0.0.0",
  "port": 8790,
  "publicUrl": "http://<树莓派IP或主机名>:8790",
  "dataDir": "/data",
  "seedAdmin": false,
  "seedUsers": [],
  "seedDriveSamples": false,
  "packaged": true
}
JSON

# 3) 跑（--platform 不必写，Pi 5 在 arm64 镜像上原生执行，不模拟）
docker run -d --name valimart-gateway \
  --restart unless-stopped \
  -p 8790:8790 -p 18790:18790/udp \
  -e NODE_ENV=production \
  -e DESK_GATEWAY_PACKAGED=1 \
  -e DESK_GATEWAY_DATA=/data \
  -v /vol1/docker/valimart-gateway/app:/app \
  -v /vol1/docker/valimart-gateway/data:/data \
  -w /app \
  node:25-slim \
  node server/src/index.js
```

要点（都有代码依据，别省）：

1. **`seedAdmin: false` / `seedUsers: []` / `seedDriveSamples: false` / `packaged: true` 必须手写**。源码里 `server/config.json` 是**开发配置**（含 `boss/boss123456` 等 7 个演示账号 + 示例公司盘），只有在 `stageGatewayApp` 打官方包时才会被 `toProductionConfig` 收成生产模板（`scripts/lib/gateway-stage.mjs`，并在 `assertGatewayStageClean` 里断言）。直接挂源码跑 ≠ 生产配置，不写 `config.local.json` 就等于带着演示账号上线。`packaged: true` 用于让网关按「已发包」的行为走。
2. **`DESK_GATEWAY_DATA` 必须指到挂载卷**，否则数据落在容器层，容器一删全没（数据目录固定优先读这个环境变量，见 `server/src/config.js:112`）。
3. **`publicUrl` 改真实地址**，否则管理页/客户端拿到的还是 `127.0.0.1` 那套。
4. **UDP 18790 建议映射**：网关默认开局域网发现信标（`server/src/lan-beacon.js`，UDP 端口 `18790`，组播 `239.255.87.90`）。容器 bridge 网络下广播/组播基本出不来，映射 `18790/udp` 也未必够——**客户端「自动发现网关」在 Docker 里大概率不生效，用 IP:8790 手动填即可**；不想要这个功能就在 `config.local.json` 里加 `"lanDiscover": false`。
5. **`node:25-slim` 是 Debian arm64**，和飞牛 OS 同为 Debian 系，不存在 glibc 不匹配问题；**Node 必须 ≥ 22**（`node:sqlite` 的要求，`server/src/store.js:2`）。别用 alpine（musl，虽然纯 JS 服务多半能跑，但没必要引入变量）。
6. **密钥进容器**：`-e DEEPSEEK_API_KEY=...`，或写进 `config.local.json` 的 `upstreams.<id>.apiKey`，或管理页「模型通道」接。三种都行，别写进镜像。
7. 单进程即可，不需要 PM2 / cluster（本来就有 `--restart unless-stopped`）。真要 compose，`docker-compose.yml` 里把上面参数照搬成 service 即可。

## 4. 方案 B：官方 Linux 包 + 换掉运行时（想用 systemd、不想常驻 Docker）

官方 `dist/valimart-harness-Gateway-linux-x64-<ver>.tar.gz` 里除了 `runtime/` 全是平台无关的：

```bash
tar -xzf valimart-harness-Gateway-linux-x64-0.1.0.tar.gz
cd valimart-harness-gateway

# 换掉 x64 node
rm -rf runtime
curl -LO https://nodejs.org/dist/v25.2.1/node-v25.2.1-linux-arm64.tar.gz
tar -xzf node-v25.2.1-linux-arm64.tar.gz
mv node-v25.2.1-linux-arm64 runtime
# 注意 install.sh 找的是 runtime/bin/node，且 npm 在 runtime/lib/node_modules/npm，
# 官方 arm64 tar.gz 的目录布局与 x64 完全一致，直接改名即可

sudo sh install.sh      # 建系统用户 thediva-gateway、生成 config.local.json、
                        # 装 /etc/systemd/system/TheDivaGateway.service 并 enable --now
```

- 默认路径：程序 `/opt/valimart-harness-gateway`、数据 `/var/lib/valimart-harness-gateway/data`、日志 `/var/log/valimart-harness-gateway`。
- 飞牛 OS ARM 版底层是 Debian，systemd 在（`install.sh` 会检测 `/run/systemd/system`）；**但飞牛把不少系统目录放在了它自己的存储卷布局下**，如果 `/opt`、`/var/lib` 不在可写的系统盘上，用 `DEST=/vol1/... STATE=/vol1/... LOGS=/vol1/... sudo -E sh install.sh` 覆盖（脚本支持这三个变量）。
- 容器里装 Docker 的飞牛更适合方案 A；**方案 B 的适用面是「飞牛装在裸机上、想用 systemd 托管」**。
- 这条路的代价：官方包名和 README 都写死 `linux-x64`，每次升级都要**重做一遍换运行时**，容易忘记 → 建议做个小脚本；或者干脆走下面 §6 的构建脚本改造。

## 5. 首次上机验收（必做，本评估没真机验证）

```bash
# 容器内先确认架构与 Node 自带 sqlite
docker exec valimart-gateway node -p "process.arch + ' ' + process.version"          # 期望 arm64 v25.x
docker exec valimart-gateway node -e "import('node:sqlite').then(m=>console.log('sqlite ok', !!m.DatabaseSync))"
docker exec valimart-gateway node --check server/src/index.js

# 服务侧
curl -s http://127.0.0.1:8790/api/health        # 期望 ok:true + product:valimart-harness
docker logs --tail 50 valimart-gateway          # 期望无 EACCES / ENOENT / 原生模块报错

# 业务侧
浏览器打开 http://<树莓派IP>:8790/admin → 首次引导设公司名 + 初始管理员
→ 员工客户端登录页填 http://<树莓派IP>:8790 → 新会话发一句 → 有回复（这一步才真正验证代理与记账）
```

要看的失败信号：容器起来即退出（多半是 `config.local.json` 拼错或 `/data` 权限）、`/api/health` 200 但管理页白屏（`plugins/desk-ui/src/client/assets/*.png` 没跟着挂进去，管理页品牌图走文件读取，`server/src/admin-page.js:13-27,42`）。

## 6. 本评估发现的四个「已知不覆盖」，别踩

1. **构建脚本只出 x64**：`scripts/build-gateway-linux.mjs` / `scripts/lib/gateway-linux.mjs` 把 `pins.nodeLinuxX64` 和产物名 `…-linux-x64-…` 都写死了。**没有任何 `dist:gateway:arm64`**。想官方出 ARM64 包，需要：`pins.json` 加 `nodeLinuxArm64`（sha256 用上面拉到的真值）、`ensureNode...` 参数化架构、产物名带 `arm64`、README 同步。约半天工作量，不难但要改 4 处并加校验。
2. **管理页的「内核试打补丁 / 发布」不要在这台 Pi 上点**：那条链会调坑里的 npm 去下载并安装 `@deepseek-ai/dsh` 及原生依赖（`server/src/api.js:13-16,1031`；`kernel-prepare.mjs` 会跑 install/postinstall 拿 `node-pty` 等原生包）。ARM64 上能不能凑齐原生产物**没验证**，且 Pi 上做这件事很慢。**内核构建继续在 Windows/x64 机器上做，再从那边发布到网关**。
3. **客户端安装包不适用于树莓派**：`client-catalog` / 管理页上传的是 Windows `Setup.exe`（`server/src/client-catalog.js:2,20`，`admin-page.js:458`）。树上**只跑服务端；员工仍然在 Windows 上装客户端**连过来。别指望「网关上了 ARM64 就能给员工发 ARM 客户端」。
4. **别用 `npm run server`（裸跑开发配置）当生产**：那条路用 `server/config.json`，会播种演示账号和示例公司盘（见 §3.1）。

## 7. 一句话回答

**能跑。** 服务端是零第三方依赖的纯 JS 服务，ARM64 原生执行不需要模拟；树的唯一障碍是官方 Linux 发行包带的是 x64 的 Node 运行时。**Docker 用 `node:25-slim`（arm64）挂源码跑，配一份 `config.local.json`（关播种 + `dataDir` 指向 SSD 卷 + 改 `publicUrl`）就能上线**；官方 ARM64 包目前没有，需要按 §6.1 改构建脚本才能有。
